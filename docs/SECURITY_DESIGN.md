# LinuxPilot AI: Action-Bound Authorization & Security Architecture Design Document

**Document Version:** 1.0.0  
**Status:** Implemented & Empirically Verified  
**Target Environment:** LinuxPilot AI (FastAPI Backend + React/TypeScript Frontend)

---

## 1. Executive Summary & Purpose

LinuxPilot AI is an AI-assisted operations agent designed to streamline system inspection, diagnostics, log analysis, file discovery, service control, and shell operations on Linux hosts. Because the system bridges natural-language intent interpretation with low-level host operating system primitives (e.g., `systemctl`, `subprocess`), securing the execution boundaries against accidental execution, prompt-injection escalation, parameter tampering, and execution desynchronization is critical.

This document details the security architecture implemented in `feature/authorization-enforcement`. Specifically, it explains the transition from a client-provided boolean confirmation flag (`confirmed: bool`) to a centralized, cryptographically bound, single-use, time-limited authorization mechanism with strict postcondition verification.

### Threat Vectors Mitigated

1. **Client Boolean Spoofing & Escalation:**
   - *Threat:* In the prior implementation, any API client or caller could pass `{"confirmed": true}` to force immediate execution of modifying commands or bypass confirmation dialogs.
   - *Mitigation:* A client-provided boolean can never independently authorize an operation. Modifying actions strictly require an active, unconsumed `operation_id` generated by the backend during a formal preview phase.

2. **Parameter Tampering / TOCTOU (Time-of-Check to Time-of-Use):**
   - *Threat:* A client previews a benign command (e.g. `chmod 755 test.sh`), receives approval, but submits the approval token with a destructive command (e.g. `chmod 777 -R /` or `apt install malicious-pkg`).
   - *Mitigation:* The authorization ticket immutably binds `action`, `target_resource`, and a canonical normalized dictionary of `parameters`. Any discrepancy between the authorized parameters and the execution parameters immediately rejects the request (`PARAMETER_MISMATCH`).

3. **Replay & Concurrency Attacks:**
   - *Threat:* An attacker captures an authorized request and re-submits it repeatedly to toggle services or re-execute state-changing commands.
   - *Mitigation:* Tickets transition atomically from `PENDING` to `CONSUMED` under a thread lock. Second or subsequent submissions are rejected (`REPLAY_PREVENTED`).

4. **Validation vs. Execution Semantic Desynchronization:**
   - *Threat:* The validator historically split chained commands on `;`, `&&`, `||`, and `|` and validated each piece, but passed the original unsplit string to `subprocess.run(shlex.split(command), shell=False)`. Because `shell=False` treats `;` or `&&` as literal arguments rather than control operators, or fails entirely, the validation interpretation diverged from the OS execution interpretation. Furthermore, redirection operators (`>`, `<`) and command substitutions (`$()`, `` ` ``) were not executed as shell commands.
   - *Mitigation:* LinuxPilot AI strictly executes argument lists with `shell=False` and rejects unsupported shell metacharacters and constructs upfront. Any presence of chaining, redirection, piping, substitution, backgrounding, or newlines results in immediate rejection (`BLOCKED / DANGEROUS`).

5. **Direct Service Endpoint Bypasses:**
   - *Threat:* Direct API endpoints (`POST /api/services/{name}/restart`, `start`, `stop`) previously executed directly if `ALLOW_COMMAND_EXECUTION=True` without any confirmation requirement.
   - *Mitigation:* Every direct service mutation endpoint now enforces the centralized authorization lifecycle. Unauthenticated requests receive an authorization preview; execution occurs only upon receipt of a valid, consumed ticket.

6. **Silent Failure & Postcondition Discrepancy:**
   - *Threat:* `systemctl restart <unit>` may return exit code 0 even if the underlying daemon crashes immediately after launching or enters a failed state.
   - *Mitigation:* The system verifies the postcondition (`check_status().active == expected_active`) after execution. Success is returned only when the command succeeds *and* the verified state matches the expected postcondition.

## 4. Authorization Data Model & Approval Lifecycle

### Ticket Schema (`OperationAuthorization`)

```python
class OperationAuthorization(BaseModel):
    operation_id: str                      # Format: op_auth_<secrets.token_urlsafe(24)>
    action: str                            # e.g., "command.execute", "service.restart"
    target_resource: str                   # e.g., "command:apt install nginx", "service:nginx"
    parameters: dict[str, Any]             # Bound canonical parameter dictionary
    expected_postconditions: dict[str, Any]# e.g., {"active": True}, {"return_code": 0}
    action_summary: str                    # Human-readable explanation of proposed action
    created_at: datetime                   # UTC timestamp
    expires_at: datetime                   # UTC timestamp (created_at + TTL)
    status: AuthorizationStatus            # PENDING | CONSUMED | EXPIRED | REVOKED
    consumed_at: Optional[datetime]        # UTC timestamp when consumed
```

## 5. Command Validation & Default-Deny Argument Policy

### Rejection of `sudo` by Default
LinuxPilot AI enforces a strict default-deny policy regarding privileged execution:
- Any command beginning with `sudo` is rejected upfront (`ValidationVerdict.BLOCKED`), even if the underlying command is read-only (e.g., `sudo df -h` or `sudo systemctl status`).
- This prevents privilege escalation and ensures automated routines cannot trigger interactive credential prompts or run commands with root privileges without explicit host configuration.

### Default-Deny Per-Command Argument Policies
LinuxPilot AI does not rely on a generic denylist regex. It implements granular per-executable validation schemas:
1. **`systemctl`:**
   - Permitted read-only subcommands: `status`, `is-active`, `is-enabled`, `is-failed`.
   - Permitted modifying subcommands: `restart`, `start`, `stop`, `reload`.
   - Modifying tokens anywhere in arguments prevent read-only classification. For example, `systemctl restart nginx status` is strictly classified as `MODIFYING` rather than `READ_ONLY`.
   - Power/lifecycle subcommands (`reboot`, `poweroff`, `halt`) are strictly `BLOCKED`.
2. **`service`:**
   - Permitted read-only forms: `service <unit> status` and `service --status-all`.
   - Modifying actions (`restart`, `start`, `stop`) require explicit action-bound confirmation.
3. **`env` and `printenv`:**
   - Safe inspection: Bare `env`, `env -0`, `printenv`, and option flags (`-u`, `--null`, `KEY=VALUE` assignments).
   - Indirect execution: Any attempt to invoke another executable via `env <command>` (e.g., `env bash`, `env python script.py`) is strictly `BLOCKED`.
4. **`find`:**
   - Safe inspection: Pattern and attribute matching (`find /var/log -name '*.log'`).
   - Dangerous flags: Options that execute programs or delete files (`-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-fprint`, `-fls`) are strictly `BLOCKED`.
5. **`ip`:**
   - Safe inspection: `ip addr show`, `ip route`, `ip link list`, `ip neigh`.
   - Modifying subcommands (`add`, `del`, `delete`, `set`, `change`, `replace`, `flush`) modify host networking and require explicit authorization.
6. **`git`:**
   - Safe inspection: `git status`, `git log`, `git diff`, `git branch`.
   - Dangerous/execution flags: `--exec-path` and `-c` configuration overrides are strictly `BLOCKED`.
   - Dangerous subcommands: `git config` and `git clean -f` are blocked from automated execution.
7. **Package Managers (`apt`, `yum`, `pacman`, `pip`, `npm`):**
   - Read-only subcommands (`list`, `search`, `show`, `view`, `outdated`) are classified as `READ_ONLY`.
   - Installation/removal operations (`install`, `remove`, `upgrade`) are classified as `MODIFYING`.

### Conservative Parsing & Intentional False Positives
To guarantee zero possibility of command injection or interpretation divergence between validation and OS execution:
- LinuxPilot AI executes strictly using parsed argument lists (`shell=False`).
- Any occurrence of shell metacharacters (`&&`, `||`, `;`, `&`, `|`, `>`, `<`, `$()`, `` ` ``, `\n`, `\r`) causes immediate rejection (`BLOCKED`).
- **Intentional False Positives:** Commands such as `echo "hello; world"` or `echo "a | b"` are rejected by the validator because they contain shell metacharacters. This is a deliberate, defense-in-depth design choice: we prioritize absolute host execution safety over complex shell string emulation.

## 6. Service Execution and Outcome Verification

State changes on system services are evaluated through a rigorous outcome verification pipeline:
1. **Canonical Binding:** The ticket binds to the canonical service unit (e.g., `sshd` maps to `ssh`, `apache` maps to `apache2`) and expected final state.
2. **Precondition Check & Idempotency Detection:**
   - Current state is inspected via `systemctl is-active <unit>`.
   - Idempotent operations (e.g. starting an already active service, or stopping an already stopped service) are detected and logged.
3. **Execution Feature Flag Independence:**
   - `ALLOW_COMMAND_EXECUTION` is checked *before* consuming the ticket. If dry-run mode is active, the ticket remains valid and unconsumed (`status == APPROVED`).
4. **Execution:**
   - Executed via `_run_systemctl([action, unit])` with `shell=False`.
   - Execution failure (non-zero return code, timeout, subprocess error) is distinguished from verification failure.
5. **Postcondition Verification:**
   - The post-execution state is queried directly using `check_status(unit)`.
   - **For `start` and `restart`:** Expected postcondition is `active == True`.
   - **For `stop`:** Expected postcondition is `active == False`.
   - If execution times out or the final state cannot be queried, the system reports an unverified outcome and **never claims success**.
   - **Verified Success Invariant:** Success is reported if and only if command execution returned exit code 0 *and* postcondition state verification succeeded.

## 8. Known Limitations & Multi-Worker Deployment Requirements

1. **In-Memory Ticket Store & Multi-Worker Deployment:**
   - Current Implementation: The `AuthorizationManager` maintains tickets in Python process memory with a `threading.Lock()`. This provides thread-safety and concurrency protection for single-worker or multi-threaded deployments (e.g., Uvicorn with `--workers 1` and thread concurrency).
   - Multi-Worker Limitation: When deploying behind multi-process application servers (e.g., Uvicorn `--workers 4`, Gunicorn, or horizontal container replicas), each worker process maintains an isolated in-memory ticket store. An approval granted on Worker A would be unknown to Worker B, leading to ticket lookup failures.
   - Requirements for Multi-Worker Production:
     * **Centralized Distributed Ticket Store:** Store tickets in Redis or a relational database with atomic transaction primitives (e.g. Redis `WATCH/MULTI/EXEC` or SQL `SELECT ... FOR UPDATE`).
     * **Distributed Locks / Compare-and-Swap:** Ensure atomic transitions (`PENDING -> APPROVED -> CONSUMED`) across workers to prevent distributed race conditions or dual-consumption.
     * **Distributed Clock Synchronization:** Ensure NTP synchronization across cluster nodes to prevent TTL skew.

2. **Audit Logging Decoupling:**
   - Database writes to `authorization_audit` are executed outside the authorization memory lock to prevent slow SQLite disk I/O from stalling in-memory checks.

3. **Host-Level Root/Sudo Privileges:**
   - LinuxPilot AI does not implement multi-tenant OS user privilege separation. If the backend process runs as `root`, executed commands execute with root capabilities. Production deployments should run the backend under a dedicated, unprivileged system account (`linuxpilot`) with restricted `sudoers` rules.

4. **Shell Script Execution:**
   - Because shell metacharacters and chaining are blocked, multi-command shell scripts must be submitted as discrete individual operations or written to a script file verified through a separate file-validation pipeline.
